> 性质：**设计提案，未实现**。

## 0. 你说得对：历史选曲不可信，而且有证据

我查了两份表：

| 表 | 段数 | 已定选 | 证据 |
|---|---|---|---|
| `黑水溪`（F:\…\026黑水溪\bgm\heishuixi.cues.json） | 13 | **0** | 只有候选，没有定选 |
| `血阳`（examples\blood-sun.cues.json） | 6 | 5 | `picks.primary.title` 为空；`why` 是**歌单描述**（「纯音乐集 · 3分」「恐怖的声音: 恐怖笑声, 鬼屋的声音…」）；`picks.at` 为空 |

血阳那五条看起来是「按歌单挑的样张」，不是逐首听过之后的判断；黑水溪更直接——一首都没选。**所以「四个模组 44 段都有手选」这个前提是假的，实际可信标注接近 0。**

后果有两层，都有害：

- 当**锚点**：会把这些采样的口味当成「公认的恐怖」，刻度从一开始就歪；
- 当**金标**：MRR 的分母是假的，后面所有「变好了」的结论都不可信。

**因此 v1 不使用任何历史标签。** 上一版里「锚点从历史选曲自动长出来」那段作废。

## 1. 去掉历史标签之后，还剩什么

| 需要的东西 | 原来打算 | 现在 |
|---|---|---|
| 分数的刻度 | 锚点（历史选曲） | **冻结参考集百分位**，零标签 |
| 描述层对不对 | 金标 MRR | **7 首客观回归**（不依赖你） |
| 决策层配得准不准 | 金标 MRR | **前瞻式**：等你真正跑团时选的那几次 |
| 历史数据怎么用 | 标注 | **只当参考分布**（只需要歌单，不需要标签） |

少了一层依赖，方案反而更短。代价要说清楚：**在头一两个真实模组之前，「配得准不准」无法用数据回答，只能验描述层的排序和一致性。**

## 2. 描述层：把 CLAP 的用法修对（不换模型）

| 病 | 现在 | 改成 |
|---|---|---|
| 只听 3 个 20 秒窗口 | v2 的 3 窗是稀疏采样 | **全曲 10 秒窗**（≤4 分钟 → ≤24 窗），跳首尾各 3 秒 |
| softmax 零和 | `analyze.py:166` | **删掉**，输出 raw 余弦 |
| prompt 措辞决定分数 | 3–5 句平均（已改善） | 保留 |
| 分数跨批不可比 | 依赖同批词表 | **冻结参考集百分位** |

### 2.1 冻结参考集：唯一刻度

- 参考集 = 现有曲目表里的全部候选（约 90–120 首）的音频向量，算一次，落盘，带版本号。
- 对每个概念 c：把参考集里所有歌的 `raw_c` 排成分布，某首歌的 `p_c` = 它在该分布中的百分位（0–1）。
- 性质：
  - **与批无关**：参考集固定，新模组加进来不改刻度（除非你主动升版本）。
  - **零标签**：不需要知道任何一首歌「是什么情绪」，只需要它们的音频。
  - **全局而非池内**：百分位是对整个参考集算的，不是对某个 cue 的 8 首候选算的——所以一个整段都不合适的 cue，分数会整体偏低，不会被迫产生一个「第一名」。
- 缺点，写在明处：**百分位是「在这个参考分布里的位置」，不是绝对概率。** 对「差不多就好」够用；要绝对概率就得有标注，见 §2.3。

### 2.2 缓存

`$DSH_HOME/bgm-prep/cache/clap/<song_id>-<vocabver>-<refver>.json`
含：`raw_c`、`p_c`、`vocal`、`stability`（窗间极差）、参考集版本。
换词表或参考集 → 新目录，旧分不残留。

### 2.3 什么时候才配锚点

只有当**你明确说某几首是认真选的**，才把歌加进锚点库。规则：

- 每个概念 ≥2 首才算数；单首不配锚点。
- 锚点库独立于参考集，存 `anchors.json`，人工维护，看得见、删得掉。
- 在此之前，所有概念一律走文本向量 + 百分位。

## 3. 词表：20 个情绪词

从现有 29 概念里只留情绪/氛围类，补两个缺口：

| 组 | 概念 |
|---|---|
| 正向 | 活泼器乐、欢快流行 |
| 正向柔和 | **温馨**（新增） |
| 负向 | 忧伤、暗色氛围、恐怖配乐、不协和低鸣 |
| 张力 | 紧张悬疑、**压迫感**（新增） |
| 宏大 | 史诗管弦 |
| 静 | 安静钢琴、安静空旷、太空氛围 |
| 动 | 律动、激烈攻击、追逐 |
| 军乐 | 军鼓行进 |
| 兜底 | 器乐（只当人声过滤，不进排序） |

- 每个概念 3–5 句英文描述（沿用 `lib/vocabulary.js`）。
- 织体类（弦乐/合唱/圣咏/合成器/电子脉冲/机械电子/打击乐/民谣木吉他/爵士/虫群/地震/暴风雨/暴乱燃烧）**移出软轴**，只在 cue 明写 `texture` 时降档。
- 为什么不用 Jamendo 的 40 个英文 mood 名直接当 prompt：CLAP 要的是自然描述，「a horror music track」这类标签名效果差；中文概念 + 3–5 句自然描述更贴场景语言。

## 4. 决策层

### 4.1 target（≤6 个权重，一次冻结）

```jsonc
"target": {
  "labels": [
    { "label": "恐怖配乐", "weight": 0.45 },
    { "label": "压迫感", "weight": 0.30 },
    { "label": "安静空旷", "weight": 0.25 }
  ],
  "vocal": "none",
  "unmapped": ["大地深处每四十秒一次的搏动"],
  "source": "auto+llm",
  "frozen_at": "2026-11-18"
}
```

- `valence/energy` → 基础权重（复用 `lib/match.js` 的优先级逻辑）。
- `wants` 的自由文本 → 概念：一次性映射、落盘、可复核，**不每次现编**。
- `unmapped` 必须写：词表表达不了的需求要能被看见。

### 4.2 打分

```
score = Σ w_c · p_c / Σ w_c
vocal: cue 要 "none" 而 p_vocal > 0.5 → 降一档
texture: cue 明写 texture 且对应织体概念 p < 0.3 → 降一档（不删）
```

### 4.3 展示

每行给 `match` + **依据**（贡献最大的 2 个概念）+ `unmapped` 标记。
「差不多就好」的前提是能一眼看出为什么，否则没法快速否掉。

## 5. 验收：分成「现在能验的」和「要等的」

### 5.1 现在能验（不依赖任何标注）

| 项目 | 通过线 |
|---|---|
| **7 首客观回归**（调研 §5.1）：期望情绪排第一、禁忌情绪不进前三 | Top-1 ≥ 6/7，禁忌 = 0 |
| **复现性**：同一首歌出现在两张表里，分数完全一致 | Δ = 0 |
| **跨批稳定性**：往参考集里加 10 首新候选后，已有歌的分不变 | Δ = 0（参考集版本不变时） |
| **区分度**：恐怖曲在「恐怖」上的分应显著高于「欢快」上的分 | 符号正确率 100% |

### 5.2 要等的（前瞻式）

从下个真实模组开始，**你在工作台里定选的每一首**才进金标：

- 每跑一个模组，记一次：你选的那首在候选池里的名次。
- 跑满 2–3 个模组（约 30–40 次定选）后，才第一次算 MRR。
- 在那之前，`match` 只当排序参考，不当「对不对」的结论。

### 5.3 可选的快速验证（不是标注音频）

如果不想等：做 **20–30 组三元组判断**——每次给你三首（A、B 应配同一类场景，C 应配另一类），你只需点「A 和 B 更像」。一次性 30–40 分钟，不需要听完整曲、不需要描述情绪。

- `triplet accuracy ≥ 90%` → 描述层够用，放心走两层架构。
- `< 70%` → 描述层不够，直接上 §6 的 music2emo，不要调权重。

> 这件事的价值在于：它测的是「能不能支撑决策」，而不是「标签像不像」。而且它是**相对判断**，比让你给每首歌打情绪标签轻松得多。

## 6. 落地顺序

| 步 | 内容 | 做完得到什么 |
|---|---|---|
| **1. 描述层 + 刻度** | 全曲分窗、去 softmax、参考集百分位、缓存 | 每首歌 20 个可比的分，同曲同分 |
| **2. 客观验收** | 7 首回归 + 复现性 + 区分度 | 第一次能用数据说「排序是通的」 |
| **3. 决策层** | `cueTarget` + 加权打分 + 依据列 | 工作台里看出「为什么是它」 |
| **4. 前瞻评测** | 记录真实定选，满 2–3 个模组后算 MRR | 第一次能用数据说「配得准」 |

前三步做完即可日常使用；第四步是持续积累，不阻塞使用。

## 7. 如果描述层不够用（唯一升级）

不动架构，只换描述层：**music2emo**（MERT 上的线性头，Apache-2.0 代码，56 个 Jamendo 情绪 + V/A）。

- 它已在 MTG-Jamendo 上训过，**不需要你标注**。
- 接口不变：还是每曲 20 个分。
- 风险：Windows 依赖（和弦解析）可能卡；卡了只取它的 ckpt + MERT embedding，绕开和弦链。

## 8. 明确不做

| 不做 | 原因 |
|---|---|
| 音效类自定义头 | 要标注 |
| instrument 轴、织体打分 | 对跑团不重要 |
| 用历史选曲当锚点/金标 | §0：不可信 |
| 训练任何模型 | 没有可信标注 |
| 每次让 LLM 判「配不配」 | 不可复现 |

## 9. 风险

1. **百分位不是概率**：分数高只代表「在这批参考曲里靠前」。UI 上不写「匹配度 87%」这种绝对口径，写「参考集第 87 百分位」或干脆只给档位。
2. **参考集代表性**：如果参考集全是某类歌单来的，分布会偏。对策：参考集里混入各模组的候选，版本化，必要时换一版重算。
3. **没有标注 → 决策层长期未验证**：这是这版方案的真实短板，只能靠前瞻数据补。别在前瞻数据出来前对外说「准」。
4. **分窗计算量**：24 窗/曲，比现在慢 3–4 倍；有缓存，只在 `bgm_tag` 触发一次。

---

## 10. 一句话

**不换模型、不标数据、不加依赖**；刻度来自冻结参考集的百分位，而不是任何一次采样出来的选择。先让描述层可复现、可解释、能排序，再等真实跑团的选曲来回答「配得准不准」。

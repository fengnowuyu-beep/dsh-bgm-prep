## 一、目标与验收判据

这次暴露的问题可以归成一句话：**用字符串匹配决定「分析哪 8 首」，再用模型给这 8 首排序。**

优化目标按优先级：

| 目标 | 现状 | 目标 |
|---|---|---|
| 候选池返工率 | 15/27 = 56% | ≤ 15%（27 段里不超过 4 段需要重抓） |
| `bgm_tag` 音频失败率 | 144/379 = 38% | ≤ 10%，且失败不复发 |
| 单模组（27 段）墙钟 | ≈ 64 分钟 | ≤ 25 分钟 |
| agent 判断池子的成本 | 只能 Python 读 JSON | 一次工具调用即可 |
| 候选池来源可解释 | 不可解释（哈希） | 每首带「为什么进池」 |

## 二、P0（不做，下次还是 1 小时 + 一半废池）

### P0-1 一阶段粗筛：不要假装会打分

**问题**：`lib/filter.js:139-181` 只用标题/艺人/专辑字符串打分；`:205-208` 同分按 `hashStr(salt:song_id) % 997` 破平 → 候选池近似抽签。

**改法（三选一，建议 A+B 组合）**：

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| A. 换破平方式 | 去掉哈希破平，改为「来源歌单主题与 cue 的相关度 → 时长 → 该段首次出现顺序」的稳定排序 | 小 | **必做**。即使分数一样，来源歌单对味的歌也该排前面 |
| B. 放大候选数 | `limit` 从 8 提到 12–16，让模型在更多候选里排 | 分析成本线性涨 | 与 P0-5 降本配套做才有意义 |
| C. 引入轻量音频判别 | 用 10–20 秒片段过一遍 CLAP 零样本做粗筛 | 大 | 不建议现在做；先把 A 做掉看效果 |

**影响面**：`lib/filter.js`、`lib/index.js`（`limit` 传参）、`test/fetch.test.mjs`
**验收**：抽 5 段人工看，top-8 里「明显不对味」的占比从当前约 40% 降到 ≤ 15%

### P0-2 `wants` 全量生效

**问题**：`lib/search.js:58` 与 `:104` 只取 `wants[0]`，与 skill 表述不符。

**改法**：两处改成 `wants.slice(0, 2)`，各搜一次歌单；`lib/search.js:141` 的歌曲搜索同理取前 2 条 query。
**若不想改代码**：至少把「**只有第一个生效**」写进 skill 与工具描述，避免 agent 写无效的多词数组。

**影响面**：`lib/search.js`、`test/fetch.test.mjs`
**验收**：一个写 2 个 wants 的 cue，检索日志里能看到两个 query 各搜一次

---

### P0-3 种子歌单不再无条件注入每一段

**问题**：`lib/search.js:156-167` 的 `loadSeedTracks` 把「我的种子歌单」最多 200 首作为 `baseTracks`
注入**每个** cue，导致 `Asuf D Alwa` / `念故乡` / `Kiss Of Death` 这类无关曲跨段污染。

**改法**：`baseTracks` 改为**按需补充**：
1. 该 cue 自己的检索结果 ≥ 12 首时，不注入种子；
2. 不足 12 首时，才从种子池里按 `target` 标签概率预过滤后补充；
3. 每段最多补 4 首。

**影响面**：`lib/search.js`、`lib/index.js`
**验收**：同一批种子曲不再出现在 3 段以上（除非确实对味）

---

### P0-4 失败负缓存 + 熔断

**问题**：`lib/analyze.js:43` 单首超时 180s；`:631` `remaining` = 所有没结果的歌 → 失败歌每次原样重试；
`:1002` `remaining = deferred + run.remaining` 疑似重复计入（实测一次 11 → 17）。

**改法**：
1. 新增 `failed_songs(song_id, reason, at, retry_after)` 表（同 `analysis.db`）；
2. 单曲失败 **2 次**后写 `retry_after = now + 10min`，冷却期内不再尝试；
3. 连续 **8 首**失败 → 熔断本次调用，返回「音源不可用，已分析 X/Y，稍后重试」，不再空转；
4. `remaining` 只统计**从未尝试过**的曲目，把「失败待重试」单独报数；
5. 排查 `deferred` 重复计入。

**影响面**：`lib/analyze.js`、`lib/analysisDb.js`、`lib/index.js`、`test/analyze.test.mjs`
**验收**：连续 3 次 `bgm_tag` 之后，「失败待重试」数不增长；返回信息能区分「已分析 / 缓存 / 失败待重试 / 未尝试」

---

### P0-5 单曲成本：只分析固定窗口

**问题**：`tools/m2e/analyze.py:21,116` 整曲下载 + 整曲 `librosa.load` + 整曲推理，250–560 秒的歌单曲 25–40 秒。

**改法**：
1. 下载改 HTTP `Range`，取前 120 秒（不足则整曲）；
2. 解码后直接裁到 ≤120 秒再推理；
3. 在 `analysis` 里记 `clip: {start, seconds}`，便于复核「分析的是哪一段」。

**影响面**：`tools/m2e/analyze.py`、`lib/analyze.js`（传参）
**验收**：单曲耗时中位数下降 ≥ 50%；同一首歌分析结果与整曲分析相比，top-2 标签不劣化

> 注意：人声识别（`VOCAL_CLIP_SECONDS` 多窗口）依赖时长，裁剪后需要确认它仍能取到足够样本。

## 三、P1（让下一次能被正确诊断）

### P1-1 `score` 字段拆成两个名字

`lib/filter.js:202` 写抓取分、`lib/score.js:97` 才是工作台用的 0–1 分，同名字段两种量纲。

- 抓取期写 `fetchScore`（字符串匹配分）
- 分析后回写 `score`（= `scoreCandidate` 的结果）
- 迁移：读表时若只有旧 `score` 且无 `analysis`，视为 `fetchScore`

**影响面**：`lib/filter.js`、`lib/store.js`、`lib/client.js`、`test/score.test.mjs`

### P1-2 `bgm_view` 列出候选

`scope=full` 现在只输出段摘要（实测）。改为每段输出候选行：`歌名 / 艺人 / 来源 / 得分 / top2 标签`，
并支持 `--candidates` 只列候选。**这是 agent 判断池子的唯一低成本通道，优先级高于 UI 改动。**

**影响面**：`lib/index.js`（工具实现）、`lib/format.js`

### P1-3 `bgm_fetch` 回传歌名

返回里每段带 top3 歌名 + 来源歌单名，让 agent **抓完就能判池子**，不必再读文件。

**影响面**：`lib/index.js`

### P1-4 `bgm_tag` 返回口径

主数字改为「本次可用 N 首 = 新分析 X + 缓存 Y」，失败与未尝试分开报。避免「已分析 0 首（缓存命中 7）」
这种看着没进展的表述。

**影响面**：`lib/index.js:916-926`

### P1-5 告警分流

现在「仅 N 首得分 ≥0.2」统一提示「减少负向标签或调低权重」，实测会误导。
改为：
- 若**全部**候选的 target 标签最高概率 < 0.25 → 报「**候选池与目标不匹配，建议换检索词重抓**」；
- 只有部分低 → 才报「负向权重过狠」。

**影响面**：`lib/score.js`（新增池子匹配度指标）、`lib/index.js`（提示文案）

### P1-6 `SEARCH_WORDS` 与词表对齐

`lib/search.js:11-21`：删掉不在 56 词表里的 `mellow / ambiental / mystery`；
补 `drama / party / retro / travel / documentary / film / movie / children / commercial / corporate / holiday / sexy / sport / summer / trailer`。

**影响面**：`lib/search.js`、`test/fetch.test.mjs`

## 六、重跑标准流程（SOP）

```text
1. bgm_init 拆表；纯调查段显式 need_bgm: false
2. bgm_fetch 全部跑完（不分析）
3. 逐段看候选（bgm_view 或看 fetch 回传的 top3）
   ├─ 池子对味 → 进入 4
   └─ 池子不对 → patch wants（歌单式命名）+ force 重抓 → 回到 3
4. 全部池子过关后，统一 bgm_tag（按 cue_ids 定向、小批推进）
5. 遇连续失败 → 停手等冷却，不要整表重扫
6. bgm_view 核对覆盖率 → 交付
```

第 3 步预计 5–8 分钟，能省掉当前约 40 分钟的返工。

## 五、未来方向：独立播放器 + 音乐包（未排期）

### 5. 把配乐工作台的结果带到别的设备上播放

> 2026-11-19 需求记录，未设计、未排期。
> 目标：备团完成后不依赖 DSH，在手机 App 和 Windows 软件里直接按场景播放。

#### 5.1 两个客户端

| 客户端 | 说明 |
|---|---|
| 独立 App（移动端） | 平台待定（Android / iOS 至少选一个先做） |
| 独立 Windows 软件 | Win10/11 x64，离线可用 |

两者共用同一套「音乐包」格式与播放逻辑，避免两套数据模型。

#### 5.2 工作台导出「音乐包」

- 入口：配乐工作台加一个「导出音乐包」按钮 / 工具（例如 `bgm_export_pack`）。
- 产物：**一个 zip**，命名建议 `<模组>-<回>-<scope>-音乐包-<yyyymmdd>.zip`。
- zip 内容：
  1. **转码后的 mp3**：只导出已定选（`picks.primary`）的曲目；从**原始音频**转码（不要用分析用的
     24 kHz mono 缓存，音质不够），建议 mp3 320 kbps，保留时长/封面等基础信息；
  2. **模组场景表**：机器可读的 `pack.json`（场景顺序、trigger、target、avoidTargets、vocal、
     选曲 song_id/标题/艺人/文件名/why）+ 一份人读的 `review.md`；
  3. **manifest**：`format: 1`、模组/回/scope、导出时间、曲目清单、文件名与 song_id 的映射、
     校验和（可选）。
- 导出行为：可断点续跑（已转码的跳过）、缺失音频要报出来而不是静默丢；导出完成前不要动已有包。

#### 5.3 导入行为（重点）

1. 用户在 App / Windows 软件里选择这个 zip；
2. 校验 manifest 与文件完整性；
3. 解压/移动到**App 或程序自己的数据文件夹**（例如 `.../MusicPacks/<packId>/`），
   不依赖原 zip 所在位置；
4. 导入成功后**删除原 zip**（按需求；实现上加确认弹窗，且只在导入+校验全部通过后删除，
   失败则保留原文件）；
5. 同一 `packId` 重复导入：覆盖或提示「已存在，替换/保留」。

#### 5.4 播放器功能（最小集）

- 按场景顺序列出段；点某段播放该段的定选曲；
- 播放/暂停、进度跳转、上/下一段、音量；
- 显示场景名、trigger、目标标签、选曲理由；
- 离线可用；切歌不打断当前场景的手动选择；
- 循环单段 / 顺序播放（开团时用）。

#### 5.5 需要先定的决策

- App 平台（Android 先做还是 iOS 先做）；
- Windows 端技术栈（Electron / Tauri / 原生，是否复用现有前端）；
- mp3 码率与是否保留封面（影响包大小，20 首约 100–200 MB）；
- 「删除原 zip」是否默认开启，还是每次勾选；
- 音乐版权口径：包只给自己设备用，不做分享/上传功能（沿用「不重新分发音频」）。

#### 5.6 风险与注意

- **转码必须用原始音频**：分析缓存是 24 kHz mono，直接转 mp3 会明显掉音质；
- 导出依赖 ffmpeg（或系统转码器），要写清楚安装/内置方式；
- 移动端存储权限与「程序自己的文件夹」在 Android/iOS 上语义不同，需分别设计；
- 大包导出/导入要有进度与失败恢复，不能卡住工作台；
- zip 删除是不可逆操作，必须先校验后删除，并在文档里写明。

#### 5.7 影响面（未来）

`lib/index.js`（导出工具）、`lib/format.js`（场景表/清单）、`lib/ui.js` + `lib/client.js`（导出按钮与进度）、
新增 `tools/export-pack/`（下载原始音频 + ffmpeg 转码 + 打包）、独立的 App / Windows 播放器工程。

## 六、2026-11-19《周而复始》实跑暴露的链路问题（待拍板）

> 报告：`docs/report-2026-11-19-周而复始配乐实跑复盘.md`
> 方案：`docs/plan-2026-11-19-检索与分析链路优化.md`
> 触发：27 段真实双幕模组实跑，64 分钟，**15/27 段候选池返工（56%）**，`bgm_tag` 音频失败 144/379（38%）。

**已核实的结论**（不是待定项，只是记下来）：

1. 候选池失真的总根源是 `lib/filter.js:139-208` —— 一阶段用**标题字符串匹配**打分，同分按
   `hashStr(salt:song_id)` 破平，导致 top-8 近似抽签；模型只在抽中的 8 首里排序。
2. `lib/search.js:58,104` 的 `wants` **只取第一个**，与 skill 表述不一致。
3. `lib/search.js:156-167` 把种子歌单无条件注入每一段，造成跨段污染。
4. `lib/analyze.js` 失败无负缓存、单首超时 180s，失败歌每次原样重试。
5. `candidates[].score` 是抓取期字符串匹配分，而工作台用的是 `score.js` 现算的 0–1 分 —— 同名字段两种量纲。
6. `bgm_view scope=full` **不输出候选行**，`bgm_fetch` 不回传歌名 —— agent 无法低成本判断池子好坏。

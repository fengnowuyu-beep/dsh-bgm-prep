> 形式：第一次用真实双幕大模组（27 段）跑完整链路：建表 → 检索 → 听感分析 → 交付候选
> 结论：**产物合格，但流程成本失控**。约 64 分钟里过半时间花在「选错池子 → 白分析 → 重抓」的返工上。

## 一、结论摘要

1. **交付是可用的**：27 段 / 197 首候选全部带 `analysis.probs`，工作台可看得分与标签。
2. **返工率 56%**：27 段里有 15 段的第一批候选池被判定为废池、重抓换词。
3. **失败的根因不在 agent 的检索词，在插件的一阶段粗筛**：
   `lib/filter.js` 用**标题/艺人/专辑的字符串匹配**给候选打分，同分用哈希破平。
   绝大多数歌名不含情绪关键词 → 一律 0 分 → 靠哈希排序 → **top-8 近似抽签**。
   模型只在「抽中的 8 首」里排序，前面抽错，后面花多少时间都救不回来。
4. **agent 侧确实有可改进的执行顺序**：应当「全部抓完 → 先看池子 → 只分析合格池」，
   实际做成了「抓一批 → 立刻分析 → 才发现不对」。这条已写进方案的 SOP。

## 三、问题清单

严重度按「对下次跑的成本影响」排。

### P0-1 一阶段粗筛是字符串匹配，同分靠哈希 —— 候选池失真的总根源

**证据**：`lib/filter.js:139-181`（`scoreTrack`）、`:192-208`（`prepareCandidates`）

打分规则全部基于 `title + artist + album` 的文本：

| 规则 | 分值 |
|---|---|
| 标题含「bgm/背景音乐/配乐/原声」 | +3 |
| 标题含「ost/soundtrack」 | +3 |
| 命中该 cue `energy:valence` 对应的情绪词（如 `burst:dark` → 史诗/战斗/黑暗/决战） | +4 |
| 命中 `CLEAN_HINT` | +4 |
| 时长 ≥ 150s | +1 |
| 命中「抖音/神曲/热歌/广场舞/土嗨」 | −8 |
| 命中该段 `avoidKeywords` | −4 |

`lib/filter.js:205-208`：**同分时按 `hashStr(salt:song_id) % 997` 排序**。

**后果**：歌名是 `Lata` / `Blast` / `Caisson` / `国色天香` 这类不含关键词的曲子一律 0 分；
0 分之间按哈希排，**等于抽签**。实测抽进去的：

- s1-07（修格斯登场）→ `Blast`（ethnic trap，party 0.90、fun 0.88）
- s1-08（盐厂逼近）→ `Kamasutra（纯音乐）`
- s2-12（米戈巢穴）→ `Arisaig`（nature 0.87 / relaxing 0.88）

**关键推论**：`bgm_tag` 只在「抽签抽中的 8 首」里排序。第一段选错，后面花 30 分钟分析也救不回来。
**这也解释了为什么换 `wants` 效果显著 —— 真正起作用的是换了个歌单，让歌名恰好带关键词的曲子被捞上来。**

### P0-2 `wants` 只取第一个，与 skill 的表述不一致

**证据**：`lib/search.js:58`（`buildQueries`）、`:104`（`collectForCue`）都是 `cue.wants[0]`。

本次每段写了 2–3 个检索词，**实际只有第一个生效**。skill 里「把 wants 里的中文检索词换一个再重试」
的表述容易被理解为多词检索，导致写多词是无效动作。

顺带：`lib/search.js:141` 的歌曲搜索也只用 `queries[0]`。

### P0-3 种子歌单全局共享，污染每一段

**证据**：`lib/search.js:156-167`（`loadSeedTracks`）一次性读出「我的种子歌单」最多 200 首，
作为 `baseTracks` 注入**每一个 cue**。

**后果**：`Asuf D Alwa`（ballad/love）、`念故乡`、`ひやむぎ、そーめん`（children/nature）、`Kiss Of Death`
这类与段落无关的曲子会反复出现在多段候选里 —— 它们不对味，只是在池子里且哈希撞上了。
`avoid.has()` 的 −6 只在跨段去重时起作用，不能解决「第一段就抽错」。

### P0-4 失败没有负缓存，单首超时 180 秒

**证据**：
- `lib/analyze.js:43` `perSongTimeoutMs: 180000`
- `lib/analyze.js:631` `remaining` = 所有没有结果的歌 → **失败过的歌下次原样再试**
- `lib/index.js:1002` `remaining = deferred + run.remaining`

**后果**：出现过连续 12 败、15 败的调用，每次 ≈10 分钟，全花在同几首死歌上。
`remaining` 也不收敛 —— 实测有一次「尝试 12 首 / 0 成功 / 剩 11」，下一次变成「还剩 17」，
疑似 `deferred` 与 `run.remaining` 重复计入（待查）。

### P1-1 `score` 字段双语义，抓取分从不更新

- `lib/filter.js:202` 写 `candidates[].score` = 上面的**字符串匹配分**（能到 8、12；命中忌讳 −6，于是有 −5）
- `lib/score.js:97-102`（`scoreCandidate`）= 工作台真正用的分：
  `Σ(权重 × 标签概率) × 负向惩罚 × 人声惩罚`，范围 0–1

同一个字段名，两种量纲。实测按 `score.js` 手算 `Cthulhu`（Frailty）是 0.76，文件里存的是 `1`。
**结果：agent 无法在文件层验证排序，只能读 `probs` 自己推** —— 而 skill 又明确要求不要自己算。

### P1-2 三处可观测性断点

| 环节 | 现状 | 后果 |
|---|---|---|
| `bgm_fetch` 返回 | 只有「已取候选：8 段，调用 33 次」 | 不告诉 agent 抓到了什么，无法当场判池子 |
| `bgm_view scope=full` | **不输出候选行**，只有每段摘要 + 状态（实测确认） | 唯一「看候选」的只读工具不干活，只能 Python 读 JSON |
| `bgm_tag` 返回 | 「已分析 0 首（缓存命中 7）」 | 主数字是 0，看着像没进展，诱导重复调用 |

### P1-3 「负向标签压得较狠」告警归因错误

告警原文：「仅 1 首得分 ≥0.2，可减少负向标签或调低权重」。

**实测反例**：s1-05 把这组负向权重从 `happy 0.30 / love 0.30 / hopeful 0.40` 调到
`0.25 / 0.25 / 0.30` 后，过线数依然是 1 —— 真正原因是池子里有 `ひやむぎ、そーめん` 这种儿歌。
告警把「池子不匹配」与「权重过狠」合并成一句，会把人引向错误的修法。

### P1-4 单曲成本是整曲级别

`tools/m2e/analyze.py:21`（「下载 → 解码成 24 kHz mono wav → 推理」）、`:116`
（`librosa.load(src, sr=24000, mono=True)` 整曲加载）。

本次候选里 250–560 秒的曲子很常见，单曲 25–40 秒。若只取 90–120 秒窗口（配 HTTP Range 下载），
成本可压到约 1/3。

### P2 结构性杂项

| 项 | 证据 |
|---|---|
| 两代打标实现并存 | `lib/tag.js:143` 仍写旧 CLAP 的 `candidate.auto`（`top/match/matchLabel`），实际数据是 `analysis.probs` + `engine: music2emo-v1` → `tag.js` 疑似死代码 |
| `SEARCH_WORDS` 与 56 词表不一致 | `lib/search.js:11-21` 里的 `mellow / ambiental / mystery` 不在词表；`drama / party / retro / travel / documentary / film / movie / children / christmas / commercial / corporate / holiday / sexy / sport / summer / trailer` 等真实标签无映射 |

## 四、对我自己执行的检讨（不推给工具）

### 4.1 顺序错了，这是浪费时间最多的一条

正确顺序：**全部 fetch 完 → 扫一遍池子 → 只对合格池跑 `bgm_tag`**。
实际顺序：抓 8 段 → 立刻分析 → 发现池子不对 → 重抓 → 再分析。
直接造成 15/27 的池子报废、约 160 次新分析里有相当一部分被丢弃。

> 校正说明：上一轮口头汇报里说的是「13 段 / 48%」，重新核对调用序列后应为 **15 段 / 56%**
> （含 s1-05、s1-09 两段先调负向权重、仍不合格后才重抓的）。本文以 15 为准。

### 4.2 补检索词时该更早换「歌单式命名」

第一轮 `wants` 写成抽象情绪词（「异样 迷离 不安」「孤独 低语 悲伤」），命中中文流行/儿歌/圣诞歌单。
第二轮换成歌单式命名才见效：

| 段 | 换词后 | 命中来源 |
|---|---|---|
| s1-04 娘娘庙 | `宗教 圣咏 恐怖` | 宗教/中世纪/神性/民俗/诡异歌单，拿到 E.S. Posthumus `Ebla` |
| s1-07 地下室 | `克苏鲁 背景音乐` | 克苏鲁歌单，拿到 Frailty `Cthulhu`（heavy 0.99 / dark 0.92） |
| s2-06 铁棺 | `太空 氛围 纯音乐` | 太空氛围歌单，拿到 Loscil `Caisson` |
| s2-15 结局 | `苍凉 纯音乐` | 悲壮磅礴歌单，拿到 Gordy Haab `杀出朝歌` |

### 4.3 重复了完全相同的工具调用

连续两次 `bgm_tag` 参数一致，被系统提示点名。当时应先读文件算覆盖率、或按 `cue_ids` 定向，
而不是整表重扫。

### 4.4 浏览器验证是一次无效尝试

为确认「工作台每行能否显示得分」开了 GUI 标签页，对着 1000+ 节点快照找，最后只 grep 到侧边栏里有
「配乐工作台」四个字，**没有任何结论产出**，还浪费两次大调用（其中一次快照溢出 57 KB）。

**结论**：这类验证应由插件提供只读自检（见方案 P2-13），不该走浏览器。

### 4.5 `need_bgm: false` 一条都没用

skill 给了判据，我没有据此把纯调查段标掉，全部配了乐。属于执行偏差，不是工具问题。

### 4.6 PDF 未声明

目录里 docx 与 PDF 并存，我没有 PDF 解析库就直接用了 docx，只在结尾一句带过。
正确做法是开场就声明「读的是哪份、为什么、另一份有什么风险」。

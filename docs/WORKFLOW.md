# 备团工作流（给 agent 的操作规则）

这份文件是这套东西真正的"程序"。插件只提供工具，判断全在这里。
规则要改就改这一份，不需要重新打包、不需要重启。

---

## 1. 什么时候开始动

| 层 | 触发 | 动作 |
|---|---|---|
| **L0 静默** | 用户贴模组、聊剧情、改设定、问规则 | **什么都不做。** 不提取、不落盘、不调工具 |
| **L1 成表** | 用户说「配点音乐」「第三幕配一下」「这段找个 BGM」「根据上次那个帮我配乐」 | 确定范围 → 回捞文本 → `bgm_init` → 把场景表给用户 |
| **L2 跑完** | 用户确认切分，或直接说「就这样」 | `bgm_fetch`（全部抓完）→ **核池子** → `bgm_tag` → `bgm_verify` → `bgm_pick` → `bgm_commit` |

### 顺序不能颠倒：先抓完、再看池子、最后才分析

一阶段粗筛只看歌名（`lib/filter.js` 的字符串匹配），它判断不了「这首对不对味」。
所以：

1. `bgm_fetch` 把要的段**一次抓完**，先不分析；
2. 用 `bgm_fetch` 回传的前 3 首歌名、或 `bgm_view` 的候选行**逐段扫一遍**；
3. 不对味的段 `bgm_init({mode:"patch"})` 换 `wants` → `bgm_fetch({force:true})` 重抓；
4. 全部过关后才 `bgm_tag`。

**换词重抓一次约 30 秒，白分析 8 首约 4 分钟。** 2026-11-19 那次因为顺序反了，
27 段里有 15 段候选池返工，多花了近 40 分钟。

### 开工前先报时长

`N 段 × 12 首 × 约 20–30 秒` 起步，失败重试另算。一次性说清楚，
并说明「分析期间不会逐段汇报」——否则用户视角是失联。

**宁可漏触发，不可误触发。**「这局想让他们紧张一点」是剧情建议，不是配乐需求。

用户只说「配点音乐」而没说范围时，默认**最近一次贴进来的那段模组/那一幕**；上下文里找不到就问一句路径，不要猜。

## 2. 从对话文本里分三种料

| 料 | 识别信号 | 去处 |
|---|---|---|
| **全局指令** | 含「整体/全程/这局/都/一直」，或「少用/别用/多一点/不要」 | `directives`，`text` 存原话，`effect` 翻成结构化（仍用于排除织体/关键词，但界面不再单独显示「全局要求」） |
| **场景** | 推进词（到了/进入/见到/发生/接着/这时）、明确地点、明确 NPC 交锋 | 一段一个 cue，按出场顺序 |
| **噪声** | 属性表、规则数值、无关设定 | 丢弃，**但在表里说明丢了什么** |

`effect` 只允许这几个键，多一个就多一处要打错：

```
valence          bright | neutral | dark
tension_bias     整数，-3..+3
energy_max       static | building | driving | burst
include_texture  ["piano","strings","drone","percussion","synth","choir","folk"]
exclude_texture  同上
exclude_keywords ["女声","鼓点"]
vocal            none | wordless
```

## 3. 判断「这一段要不要配乐」

**20 个场景通常只需要 8~10 首。** 每 5 分钟切一次音乐会让人麻木。

**要给**：情绪强度高（对峙 / 揭示 / 战斗 / 告别）、有大段台词需要垫底、明显转场。
**不给**：纯调查、规则结算、NPC 闲聊、连续小场景（沿用上一段底噪更自然）。

判不准时按「给」处理，留给用户删——删一行比补一行便宜。

---

## 4. 打标签

按**演出功能**打，不按曲风。

```json
{ "tension": 6, "valence": "dark", "energy": "static",
  "texture": ["drone","strings"], "vocal": "none", "min_len": 180 }
```

- `tension` 0–10：能不能盖过说话声。3 以下只做底噪，7 以上抢注意力。
- `energy`：static 不推进 / building 渐强 / driving 持续推进 / burst 爆发。
- `vocal`：默认 `none`；合唱、吟唱、和声可标 `wordless`；有可辨歌词的 `lyrics` 不选。
- **`vocal` 会真的影响排序**（0.13 起）：分析后用 CLAP 探测「有没有人在唱」，
  `none` 的段会对人声概率高的候选乘性压低（默认最多 −25%），`any` 半额，`wordless` 不罚。
  所以给需要台词垫底/独白的段写 `none`，给气氛段写 `any` 更稳。
- `texture` 从固定枚举里挑，别自造词（`include_texture` 要能匹配上）。

**安静场景降权规则**：`energy: static` 或场景属「独白 / 对峙」时，`wordless` 降权、`none` 优先。理由：安静场景里突然出现的人声（哪怕只是和声垫）会把注意力从台词上拽走。

### 负向标签（`avoidTargets`）

「这段要多黑暗」好说，「别给我欢快」难说。有这类诉求时写 `avoidTargets`：

```json
"avoidTargets": [{ "tag": "happy", "weight": 0.5 }, { "tag": "upbeat", "weight": 0.5 }]
```

- **3–5 个**，按场景自己判断给几个，**不要凑满**；
- 与 `target` 完全独立，**不要写成负数塞进 target**；
- 每个场景的权重可以不同：权重按实际数量归一化，表格/工作台会如实写出每个标签的权重（如 `欢快 0.40 / 轻快 0.30`）；
- 只是**压低概率**，不剔除候选；乘性惩罚最多压 60%；
- 每个标签独立计分，不去重、不合并——`happy` 与 `upbeat` 都写就各自算；
- 宁可少写：写错一个标签会把整段候选压偏；用户可以在工作台「负向标签：」那一行里增删、直接改权重。
- 工作台「设置」里有总开关：关掉后打分不乘惩罚、检索也不按标题关键词筛。

### 检索词（`wants`）怎么写

`wants` **前两条都会生效**（playlist 检索与歌曲检索各用一条），写法的差别是数量级的：

| | 写法 | 结果 |
|---|---|---|
| ✅ | `克苏鲁 背景音乐`、`宗教 圣咏 恐怖`、`太空 氛围 纯音乐`、`苍凉 纯音乐`、`战斗 纯音乐` | 命中按主题策展的歌单，池子整体对味 |
| ❌ | `异样 迷离 不安`、`孤独 低语 悲伤` | 命中华语流行 / 儿歌 / 圣诞歌单，池子全是废曲 |

网易云的检索是**歌单标题匹配**，所以要写「像歌单名」的词：
`<主题> <用途>`。抽象情绪词几乎必然踩坑。

`bgm_tag` 报「候选池与目标不匹配」时，走的就是这条：换词重抓，**别去调负向权重**
（那是另一种毛病的修法）。

### 分析失败怎么办

- 拿不到音频的歌会进 **10 分钟冷却**，下次 `bgm_tag` 自动跳过；连续 8 首失败会熔断本次调用。
- 看到 `failed` / `retryLater` 不要整表重扫：等冷却过去，用 `cue_ids` 定向补那几段。
- 冷却中的歌仍可在工作台试听，只是没有得分与标签概率——交付时要说明这一点。

## 5. 选曲

### 只能从候选里挑

`bgm_pick` 会校验 `song_id` 是否在该段 `candidates` 里，不在就整条拒绝。**不要凭记忆报歌名。**

### 每段定 1 主 + 最多 2 备

主选是"拿来就能用"的那首。备选不是给用户挑的，是主选不能用时的替补——所以表里默认只显示主选。

### `why` 写具体特征，不写形容词

- ✅ `低频垫底无鼓点，弦乐中段才抬一次`
- ❌ `很有压迫感，适合这个场景`

限 30 字。这句话是用户唯一能验证"你有没有听懂"的地方。

### 被否定过的先排除

写进 `reject`。重跑时先排除这些，避免反复回炉。`bgm_pick(reset: true)` 可清空。

## 6. 表的版式（不要改）

**表内只有一个编号：`第 k 段`。** `c0x` 只进文件，不进表——用户会说"第 3 段太吵"，两套编号会指错。

**L1 场景表**（`bgm_view --scope cues`）

```
猩红文档 · 第三回 · 第三幕          共 7 段 / 5 段需配乐

第 3 段  地窖 · 石桌与封蜡信
        玩家走下石阶，看见石桌上未拆的信
        [暗 / 静态 / 弦乐/无人声]

第 4 段  档案室 · 翻卷宗                            —— 不配乐
```

**L2 曲目表**（`bgm_view --scope full`）

已定选的段：

```
第 3 段  地窖 · 石桌与封蜡信              [暗 / 静态 / 弦乐]
        01 曲名 — 艺人                   4:05
        低频垫底无鼓点，弦乐中段才抬一次        备选 2
```

还没定选的段会逐首列出候选（`candidate_limit` 默认 6）：

```
第 4 段  走廊 · 涟漪门                    [黑暗 / 深度 / 太空]
        —— 待选（候选 12）
        01 Caisson — Loscil · 7:49 · 得分 0.62 · 深沉 88% / 氛围 71% · 出自《太空氛围之声》
        02 …
```

- `得分` 是 **0–1 的段内得分**；`未分析（关键词分 N）` 表示这首还没跑 `bgm_tag`。
- 规则：
  - **不要用空格手工对齐**——中日文混排 + 比例字体必错位。
  - **不要用 `<details>` 折叠**——聊天渲染未验证。
  - 完整的备选只在 `review.md` 里，不在聊天里。

## 7. 什么时候停下来

| 情形 | 行为 |
|---|---|
| **首次为某个模组跑** | **停**：先给 L1 场景表，等一句"可以"再跑 |
| 同模组第二次起，需配乐段 ≥ 8 | 停 |
| 其余 | 不停，直接跑到 L2 |

理由：L1 的价值是校验**提取口径**，只有第一次是未知量。

## 8. 用户改口怎么处理

| 用户说 | 动作 |
|---|---|
| 第 3 段太吵 | 只重跑该段：`bgm_fetch({cue_ids:["c03"], force:true})`，重排后 `bgm_pick` |
| 整体再暗一点 | 改 `directives` → `bgm_init({mode:"patch"})` 更新 → 全量 `force` 重取。**跑前告诉用户大概要调多少次接口** |
| 这首不行 | 备选顺位顶上，旧曲写进 `reject`，不重新检索 |
| 不要这段 | `bgm_init({mode:"patch", cues:[{id, scene, need_bgm:false}]})`，表里留一行「—— 不配乐（已移出）」 |
| 加回第 4 段 | 同上，`need_bgm:true`，然后单独 fetch |

## 9. 收尾

`bgm_commit` 会**真的把歌单建到账号里**：

1. 歌单名：`<模组>·S<回>·<scope> · 主选`
2. 表里没记过 `playlist_id` 就新建，记过就复用它（幂等，不会每次多建一张）
3. 按段序把主选曲目的**加密 id** 加进去；已在歌单里的跳过
4. 同时导出三个文件：`review.md` / `playlist.txt` / `playlist.csv`

`dry_run: true` 只报告会加几首，不写账号。

**拆了 scope 要一次合表**：`bgm_commit({files: ["s1-caozhuang.cues.json", "s2-migobase.cues.json"]})`
→ 一个歌单，段序按数组顺序；`review.md` 按 scope 分节。
分两次 commit 会变成两个歌单，跑团时还得来回切。

**加曲用的是加密 id**（32 位 hex），不是数字 id —— 候选里两个都存了，别取错。

## 10. 常见误判

- **把"这一段很重要"当成"要配乐"**。重要性 ≠ 需要背景音乐。大段推理、谈判反而需要**更淡**的底噪，或者干脆静音。
- **一段配多种情绪**。一首曲子只有一个情绪曲线。要"从压抑到爆发"就拆两段。
- **给战斗配"燃曲"**。跑团战斗通常持续 20 分钟以上，燃曲 3 分钟就到了，剩下 17 分钟在重复副歌。战斗更需要**循环友好、无强记忆点**的推进型曲子。
- **忽视时长**。`min_len` 是"一段对话不循环的最短时长"，不是随便写的。

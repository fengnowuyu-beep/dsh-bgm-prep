# 备团配乐（bgm-prep）

输入是**场景清单**（一行一段），输出是「场景 → 歌」的表 + 网易云歌单。
机器只负责捞候选和排序，**定选永远由人做**。

## 开工前要知道的四件事

1. **目标（target）= music2emo 的 56 个原生英文标签 + 权重**。不是中文概念，权重会自动归一化，最多 6 个。
2. **词表以 `$DSH_HOME/bgm-prep/moods.json` 为准**；读不到时用本 skill 同目录的 `moods.json` 快照。
   **不要读插件源码去推词表**——那是重复劳动，而且可能是旧版本。
3. 曲目表是 schema 2，路径惯例 `<模组目录>/bgm/<scope>.cues.json`。所有写操作走工具，不要手改文件。
4. **先报时长**：按 `段数 × 每段候选数 × 单首耗时` 估个量级并说出来（单首约 3–5 秒，见「§4 分析听感」），
   并说明「分析期间不会逐段汇报」。2026-11-19 那次 27 段跑了 64 分钟、中途零反馈，用户视角是失联。

## 默认做到哪一步

用户说「整理模组歌单 / 剧本歌单」且没有额外说明时，**默认一路做到能逐首看到候选与得分**：

1. 建表：`bgm_init`
2. 找候选：`bgm_fetch` —— **全部跑完，先不分析**
3. **先核池子**：看 `bgm_fetch` 回传的前 3 首，或用 `bgm_view` 逐段看候选行。
   不对味的立刻 `bgm_init mode=patch` 换 `wants` + `bgm_fetch force:true` 重抓
4. 池子过关后再 `bgm_tag`：这一步最贵，只对合格池做
   - 拿不准某段行不行时，先跑 `bgm_tag({probe: true})`：每段只看前 3 首，返回各段 `poolMatch`。
     几段一共 1 分钟左右就能判出「哪段要重抓」，比跑完全量再发现便宜得多。
5. `bgm_verify` 自检 → 交付候选，让用户在工作台试听定选

**默认停在这里**：候选可见、带得分与标签概率。**不自动定选、不自动建歌单**——那是人做的。

只有这几种情况提前停，并说明原因：

- 用户明确说「只要清单 / 先别找歌 / 不用分析」；
- 登录失效或检索不可用 → 停在建表；
- music2emo 环境不可用 → 停在候选，并明确说「分析未做，没有得分」。

## 流程

### 1. 建表：`bgm_init`

- 一行一段：`scene` 必填；`trigger` 一句话上下文。
- **`need_bgm: false` 要真的用**（判据见 §附录 A）：纯调查、规则结算、长段对话不该配乐。
- **target 可以先不写**：工具会按中文描述自动预填 3–6 个标签。
- 返回后看三样：
  - `unmatched`：**描述未命中标签**的段——目标暂时是 `calm`，需要手写 target；
  - `dropped`：写了词表外的标签，已被丢弃；
  - `needBgmHints`：像是纯调查却标了要配乐的段——检查是不是该改成 `need_bgm: false`。

### 2. 需要手写 target 时

- 从 `moods.json` 的 56 个词里挑 **3–6 个**，权重写正数即可（会自动归一化）。
- **主干优先用模型预测强、区分度高的标签**：`dark` `dramatic` `heavy` `sad` `calm` `meditative`
  `epic` `energetic` `relaxing` `powerful`。`space` `deep` `soundscape` `dream` 这类概率普遍偏低，
  拿来当主干会让所有候选的得分一起趋近 0、排序变平，只适合做低权重的点缀。
- 中文感受没有对应词时，用组合表达。例：
  - `恐怖` → `dark` + `dramatic` + `heavy`
  - `温馨` → `soft` + `hopeful` + `love`
  - `废墟` → `calm` + `space` + `sad`
- 不要把中文当标签，不要发明模型不认识的词。

### 3. 找候选：`bgm_fetch`

- 单次能处理几段有上限（工具会提示还剩多少）；每段留几首由 `candidateLimit` 决定，默认比一段能用的数量多。
- **`wants` 的前两条都会生效**；写法决定成败：
  - ✅ **歌单式命名**（按主题策展，命中率高）：
    `克苏鲁 背景音乐`、`宗教 圣咏 恐怖`、`太空 氛围 纯音乐`、`苍凉 纯音乐`、`战斗 纯音乐`、`战争配乐`
  - ❌ **抽象情绪词**（会命中华语流行/儿歌/圣诞歌单）：
    `异样 迷离 不安`、`孤独 低语 悲伤`
- 一次抓完就**先看池子**，别急着分析。判据：top 3 里有没有「明显不是这个世界的曲子」。
- 响应很便宜、分析很贵：**换词重抓一次 ≈ 30 秒，白分析 8 首 ≈ 4 分钟**。
- 候选是工具从网易云搜来的；**你没有资格自己写歌名或 song_id**。

### 4. 分析听感：`bgm_tag`

- **只对合格池做**。默认必做，否则没有得分和标签概率。
- 调 music2emo，按歌缓存；单曲只取开头 120 秒，首次约 15–30 秒。
- 单次调用有首歌上限（`max_songs`）。返回 `remaining > 0` 时**再调一次**，不要换工具；返回里会带 `timings`，
  直接告诉你每首各环节多少毫秒、模型加载几次——不用再自己计时。
- **失败是正常的**：拿不到音频的会进 10 分钟冷却，连续 8 首失败会熔断整次调用。
  这时**别整表重扫**——看返回的 `retryLater`，等冷却过去再定向补（`cue_ids`）。
- **结果逐首入库**（`$DSH_HOME/bgm-prep/analysis.db`）：中断最多丢当前一首；同一首歌以后直接取。
- 输出：56 个概率 + valence/arousal + 段内得分（0–1，会写回 `candidate.score`）。
- 单首 `KeyError: 'X'`（未知和弦）已由 `tools/m2e/analyze.py` 的运行期垫片兜住；若还出现，说明垫片失效，按错误上报，不要换歌。
- **只改了 target / 负向权重、想刷新得分**：直接再跑一次 `bgm_tag`。没有新歌要分析时它只重算得分、不跑模型，
  返回里的 `scored: N` 就是重算的条数。

### 5. 看表并交付：`bgm_view` / `bgm_verify`

- `bgm_view scope="full"` **逐首列出候选**：`歌名 — 艺人 · 时长 · 得分 · 两个标签 · 出自哪个歌单`。
  `candidates: false` 只看段摘要；`candidate_limit` 控制每段列几首（默认 6）。
- `bgm_verify` 做交付前自检：每段的 候选数 / 已分析数 / 池子匹配度 / 达标数 / top1 得分，
  并把「池子不对味」和「权重压太狠」分开报。
- **得分字段只有一种含义**：0–1 的段内得分。抓取期的关键词分在 `fetchScore`，两者别混着读。

### 6. 人定选

- 让用户在工作台试听（完整播放器），或用户直接给 `song_id`。
- `bgm_pick` 的 `song_id` **必须来自该段 candidates**，否则整条被拒绝。
- `why` 写具体特征，30 字以内；不要写「好听」「合适」这种空话。

### 7. 出歌单：`bgm_commit`

- 幂等：同名歌单会复用，只补没加过的曲子。
- 建完会把「场景 → BGM」对照写进**歌单说明**（网易云里点开歌单就能照单配乐）；
  每次都会覆盖，手工改过的说明会丢。超长时会自动压缩并注明「其余见 review.md」。
- 同时导出 `review.md` / `playlist.txt` / `playlist.csv`。
- **拆了 scope 就一次合表**：`files: [第一幕.json, 第二幕.json]` → 一个歌单、段序按数组顺序。
  不要分两次 commit（会变成两个歌单）。

## 规则

| 规则 | 说明 |
|---|---|
| **`force` 会覆盖生产缓存** | 同一首歌重算后写回 `analysis.db`，之前的结果就没了。测试新配置请用独立 `$DSH_HOME`，别拿正在用的曲目表试 |
| **先抓完再看池子，最后才分析** | 一阶段粗筛只看歌名，先分析等于给坏池子烧钱。2026-11-19 因此返工 56% |
| **默认端到端** | 说「整理歌单」就做到候选带得分可见；不要停在「只建了表」或「只找了候选」 |
| 候选只能来自工具 | 不许凭记忆写歌名；`bgm_pick` 会校验 |
| 每段 3–6 个标签 | 超过 6 个会被截断 |
| 只在段内排序 | 得分是「按这段权重算的」，不要跨段比 |
| 差不多就好 | 目标是在每段候选里大致排对，不是判对情绪 |
| 一次 10–20 段 | 超过就拆 scope；最后用 `bgm_commit files` 合表 |
| 不读插件源码 | 词表在 `moods.json`，用法在本 skill |
| 不自动拆模组 | 场景由用户提供；你只负责整理和调用工具 |
| 不替人做最终选择 | 得分只是排序参考；定选和建歌单要等人发话 |

## 收尾检查

- `bgm_verify` 过了吗（每段已分析数 = 候选数，池子匹配度正常）；
- `unmatched` 的段补齐 target 了吗；
- `needBgmHints` 里的段确认过要不要配乐吗；
- 每段状态：已选 / 待选 / 不配乐；
- 歌单里的曲目顺序 = 场景顺序（等用户定选后才建）。

## 附录 A：`need_bgm` 判据

**设为 `false`**：

- 纯调查取证：翻档案、对照片、查资料、盘问 NPC 且不推进场景；
- 规则结算：战斗回合结算、理智检定、技能成长、购物；
- 长段对话：复盘、商议计划、彼此交代设定；
- 阅读长文本：让玩家自己读线索清单。

**保持 `true`**：

- 场景切换、进入新地点；
- 任何「描写环境」的段落；
- 战斗、追逐、仪式；
- 情绪转折点（发现真相、目睹死亡）。

拿不准时保持 `true`，交付时在说明里点出「这段是纯调查，也可以不配乐」。

## 附录 B：本 skill 对应的工具

| 工具 | 作用 |
|---|---|
| `bgm_init` | 建表 / append / patch / replace；返回 unmatched、dropped、needBgmHints |
| `bgm_fetch` | 检索候选；回传每段前 3 首歌名，便于立刻判池子 |
| `bgm_tag` | 听感分析；失败进负缓存，连败熔断；返回可用/新分析/缓存/待重试 |
| `bgm_view` | 只读看表；full 模式逐首列候选 |
| `bgm_verify` | 只读自检；分开报「池子不对」与「权重过狠」 |
| `bgm_pick` | 落定选（必须来自该段 candidates） |
| `bgm_commit` | 建歌单 + 导出三件套；`files` 支持跨 scope 合表 |
